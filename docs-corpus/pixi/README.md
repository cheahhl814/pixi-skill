The `features/*.md` files are the **upstream Markdown source** at the release tag matching the
installed binary, fetched from
`https://raw.githubusercontent.com/prefix-dev/pixi/<tag>/docs/...`. Using the git-tagged
source (rather than a scrape of the rendered site) keeps the corpus version-pinned to
the binary and free of HTML-to-markdown conversion artifacts. The rendered pages are
kept alongside in `_raw/*.html` for the cases where the Markdown source alone is
ambiguous. When refreshing, bump the tag to match `pixi --version`:

```bash
TAG=v0.83.0
BASE="https://raw.githubusercontent.com/prefix-dev/pixi/$TAG"
curl -sSfL "$BASE/docs/reference/pixi_manifest.md" -o features/reference_pixi_manifest.md
# ...same for the other docs/ paths in the table above
```

## Freshness

`cli-reference.md` is regenerated by running `./capture.sh` against the currently-installed
`pixi`. The subcommand list is **derived** from `pixi --help` at capture time, not
hardcoded — pixi added `auth`, `config`, `exec`, `import`, `reinstall` and `upgrade`
between 0.81 and 0.83, and a hardcoded list silently goes stale. `pixi global`
subcommands get a second-level capture because the global-vs-project decision is the
one agents get wrong most often.

```bash
./capture.sh
```

`cli-reference.md` is ground truth for CLI flags/behavior; `features/reference_pixi_manifest.md`
is ground truth for `pixi.toml` schema.

## Feature gaps found vs. the skill's Procedure/Pitfalls (see parent SKILL.md)

Surveyed beyond init/add/task/install/list. Notable pixi features not previously covered in `SKILL.md`:

- **Multi-environment / features** (`[environments]`, `[feature.<name>.*]`) — share or split dependency sets across dev/test/prod without separate projects. `pixi run -e <env> <task>`.
- **`pixi global`** — separate manifest-driven system for exposing CLI tools globally (distinct from project-local `pixi add`); has its own `add/install/expose/sync/uninstall`.
- **`pixi task add --depends-on`** — build task DAGs (e.g. `qc` depends on `trim` depends on `fastqc`), with per-task `cwd`, `env`, and caching (`--input`/`--output`).
- **`pixi workspace requires-pixi`** — pin a minimum pixi version in the manifest so `pixi install` refuses on an outdated pixi.
- **`pyproject.toml`-native workspaces** (`[tool.pixi]`) — pixi can manage the environment for a project that already uses `pyproject.toml`, including PyPI editable installs (`pixi add --pypi --editable`).
- **`pixi workspace export conda-environment` / `conda-explicit-spec`** — export a pixi-managed env to a plain `environment.yml` or explicit spec, useful for handing off to non-pixi collaborators or Docker base images.
- **`PIXI_*` environment variables** (`PIXI_NO_PROGRESS`, `PIXI_COLOR`, `PIXI_NO_CONFIG`, etc.) — useful for CI/agent contexts (non-interactive, no ANSI color).
- **`pixi shell-hook`** — print the activation script instead of dropping into a subshell; needed when the calling process (an agent) must activate the env in its *own* shell rather than spawning a nested one.

Added in the 2026-10-28 refresh (pixi 0.70.1 → 0.83.0):

- **`exclude-newer` (workspace-level manifest key)** — excludes every package published after a cutoff (RFC 3339 timestamp, `YYYY-MM-DD` date, or a relative duration such as `"7d"`) from the solve of *every* environment in the manifest. This is the strongest reproducibility lever pixi offers: it makes a re-solve on a future machine pick the same artifacts even if a lockfile is not carried along. Also supported in the **global** manifest since 0.82.0.
- **`[project]` is the deprecated alias for `[workspace]`** — not the reverse (pixi 0.83.0 changelog #7086). A `[project]`-headed manifest still parses but emits `WARN The 'project' field is deprecated. Use 'workspace' instead.` on every command that reads it. Emit `[workspace]`.
- **`pixi global` channel default** — conda-forge is the *only* default channel for `pixi global` (0.83.0 changelog #7285). Bioconda tools need an explicit `--channel bioconda`; the project-local channel list in `pixi.toml` does not apply to global installs.
- **`pixi global` isolation model** — each globally installed package gets its own environment with only the needed entry points exposed (pipx-like). `--with` adds sibling packages without exposing them; `--expose name=bin` renames an exposed binary. This is why `pixi global` is safe for standalone CLI tooling and wrong for a skill's own tool inventory.
- **New subcommands since 0.81** — `auth`, `config`, `exec`, `import`, `reinstall`, `upgrade` (all captured in `cli-reference.md`).
